# UX044 — Separate payment-preview API backend and Cloudflare edge

**Implemented as reviewable infrastructure code. Not deployed, no project/database provisioned, and no Paystack dashboard URL changed.**

## What the milestone adds
- A **new AWS CloudFormation stack** `hustle-payment-preview-api` in account `707859598737`, region `eu-west-2`, separate from `hustle-isolated-lambda-staging`. It defines its own Lambda, log group (3-day retention) and minimal logging-only execution role; no production resources, S3 write role, extra credit providers or shared AWS secrets. An immutable SHA256 image from **dedicated ECR repository** `hustle-payment-preview-api` is required.
- A separately named **Cloudflare API Worker** `hustle-payment-preview-api`, bound to the reserved `https://hustle-payment-preview-api.realxpens.workers.dev` origin. It forwards only API and Auth endpoints to a checked dedicated Lambda URL (not the known existing staging Lambda), preserves exact Paystack-signed raw webhook bytes and never embeds database/provider secrets. Existing iPhone staging and AWS preview Workers are unchanged.
- The new `.github/workflows/hustle-payment-preview-api-deploy.yml` is only triggered manually on `main`, after the exact consent `I_AUTHORIZE_NEW_PAYMENT_PREVIEW_API_ONLY` and **new protected GitHub environment** `hustle-payment-preview-api`. It requires the approved new Neon project ID, branch ID and host, an existing new ECR repo, dedicated Secrets Manager secret and new GitHub AWS OIDC role. It validates AWS identity, standalone stack, backend health and anonymous 401 payment read before any Cloudflare API Worker deployment.
- Full offline route and HMAC-byte preservation assertions; static infra/deployment deny tests added to isolated payment CI. No actual provider, AWS, Neon or Cloudflare calls in PR CI.
- The previously merged UX042 startup boundary still requires separate `hustle_payment_preview` database and `payment_auth` auth schema. It refuses known staging hosts and projects, any live Paystack key or missing `sk_test_` test key.

## Important limitations and concrete prerequisites
**Do not run the new deploy workflow until explicitly approving actual infrastructure creation** and the following independent resources have been reviewed and provisioned. Merging the PR alone is safe and **does not create or update anything**.

1. New *unrelated* nonproduction Neon project in London with new branch, no copy or branching from production/staging. Create database `hustle_payment_preview`, restricted role `hustle_payment_preview_api`, `public` and `payment_auth` schemas; apply existing reviewed Prisma migrations and the isolated auth schema to only the new DB. Neon free-plan limits, resource usage and pricing need review first. The connected Neon account currently lacks this project.
2. New AWS IAM OIDC trust role `hustle-github-payment-preview-deployer` scoped to this repository + the protected `hustle-payment-preview-api` GitHub environment, least-privilege rights to **only** new preview ECR/CloudFormation/IAM/Lambda/log resources; no broad production permissions.
3. New ECR repository `hustle-payment-preview-api` and new AWS Secrets Manager secret **`hustle-payment-preview-credentials`** in account `707859598737`. JSON keys: `DATABASE_URL`, `STAGING_AUTH_DATABASE_URL`, `BETTER_AUTH_SECRET` (separate random >=32), `HUSTLE_STAGING_TEST_EMAILS` (invited internal test emails only) and `PAYSTACK_TEST_SECRET_KEY` (private `sk_test_` only). Do not store or print credentials in workflow inputs/PRs. DB URLs must be nonpooled TLS and point **only** to the new database/role with `schema=public` and `schema=payment_auth` respectively.
4. GitHub environment `hustle-payment-preview-api` with restricted `main` deployments, required human reviewers, separate **Cloudflare** deploy token restricted to `hustle-payment-preview-api` only. Do not reuse an unscoped staging deployment token. Review and approve new infrastructure spend and the fact a function URL with `AuthType: NONE` is **public**, guarded by Nest's route policy, authentication, Paystack HMAC and independent provider verification. This is for restricted internal test users, not customer use.
5. Only then run the manual API deploy on `main` with reviewed Neon identifiers. It first validates the Lambda's health, rejects anonymous payment reads, then publishes the separate API Worker and checks its health; **never** writes a Paystack dashboard webhook URL. If it fails after CloudFormation creation, the dedicated Lambda resource may persist and must be reviewed or removed explicitly.

Once the independent API passes, **the already merged UX043 Web deploy workflow** can publish the separate `hustle-payment-preview` app. Then invite internal testers and use official Paystack test cards to validate actual app login, product order, paid booking, verified return, webhook, stock, ledger and one-time escrow release.

### Rollback
Disable the separately named Cloudflare API Worker, dedicated Lambda stack and test project after reviewing stored synthetic evidence and resources. Never roll back by deploying/rewiring existing `hustle-ios-pwa-staging`, `hustle-isolated-lambda-staging` or production systems. This still does **not** activate live payments, payouts or regulated financial custody.
